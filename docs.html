Before you start

Use https://api.chainmore.io as the API base URL. Keep merchant API keys on your server, never in a browser bundle or mobile app.

  • Create the appropriate API key in your merchant dashboard. A cm_test_… key selects test mode; cm_live_… selects live mode. Do not pass a mode override in the request.
  • Configure your merchant settlement profile and payout destinations. Payment methods depend on those settings and the enabled routes; a new link can return an empty method list.

Test mode is not a guarantee of simulated blockchain activity. A wallet transaction can still use a public network and real assets. Do not sign or fund a test payment unless its network and cost are understood.

01Create a checkout link

POST/v1/checkout/links

This example requests USD 10.00. amount_minor uses currency minor units: 1000 cents, not token atomic units. Set the environment variable on your server and use a unique idempotency key for each order.

curl https://api.chainmore.io/v1/checkout/links \
  --request POST \
  --header "Authorization: Bearer ${CHAINMORE_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: order-1048-checkout" \
  --data '{
    "amount_minor": 1000,
    "currency": "USD",
    "merchant_order_id": "order-1048"
  }'

Read checkout_link_id, checkout_token and available_payment_methods from the response. Store the link ID with your order. The checkout token is returned only on initial creation, not an idempotent replay.

For configured same-chain USDC acceptance, an additional usdc block is not required. Explicit USDC routing details are available in the request reference.

02Send the customer to checkout

Build the customer URL from the returned checkout token, URL-encoding the value:

https://checkout.chainmore.io/checkout/?token=<checkout_token>

Only show payment options returned for this link. The hosted checkout handles the customer's method selection and wallet interaction. Your merchant API key must never be added to this URL.

03Confirm the outcome

GET/v1/checkout/links/{id}

A link becoming bound means that a payment method was selected, not that the order is paid. Follow the returned payment_id or intent_id through its corresponding status endpoint.

Register a webhook endpoint with POST /v1/webhook_endpoints. Verify X-ChainMore-Signature as a lowercase-hex HMAC-SHA256 of the exact raw request body, using your endpoint secret. Compare signatures in constant time and deduplicate by event id.

Fulfil the order only after the relevant settled event or confirmed terminal payment state. A browser return, wallet submission or transaction hash alone is not a settlement confirmation.

Errors and safe retries

For merchant mutations, send an Idempotency-Key. Retry the same logical operation with the same key and request body; do not create a new operation just because a response was lost.

Read the machine-readable code in the problem response and retain the correlation ID for support. Authentication failures, unavailable methods and validation errors require correction before retrying. The endpoint reference lists applicable responses and authentication requirements.

Server API keys and dashboard login tokens are different credentials. Use the credential required by the endpoint; dashboard-only operations cannot be called with a merchant API key.
