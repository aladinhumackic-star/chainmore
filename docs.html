Your server creates a payment. Your customer pays on our checkout page. We tell your server when the money has arrived. Five steps, all of them below.

Before you start

  • Account. You need a ChainMore account. Request access; we review every company and reply by email. You start in test mode.
  • Two addresses. The API is https://api.chainmore.io. The checkout page is https://checkout.chainmore.io.
  • API key. Create one in the dashboard under API keys. A key that starts with cm_test_ works in test mode, cm_live_ in live mode. It is shown once. Keep it on your server only, never in a browser or app.
  • Where your money goes. Add a receiving target in the dashboard under Receiving targets. Only the account owner or an admin can add one; the finance role can view them. Without a target, the checkout has no payment method to offer. Targets belong to a mode: the ones you add in test mode do not apply in live mode.
  • What your customers can pay with. A USD link offers USDT and USDC. Today that is USDC on Ethereum, Arbitrum, Base and Polygon, and USDT on Ethereum, Arbitrum, BNB Chain and TRON. The checkout offers a network where you have a receiving target for that token, or from where the money can be sent on to one of your targets. Which of these apply depends on your targets and your agreement with us. Card payments exist only for EUR links in test mode; a live EUR link has no payment method.
  • Fees. ChainMore's fee depends on the payment method and your agreement with us. Part of it can be added on top of the invoice for the customer, part can be deducted from what you receive. Both are taken once, in the same payment. The checkout shows the customer the total before they confirm. The customer's wallet pays the network fee.

Test mode uses real money for stablecoins. USDT and USDC payments in test mode run on the real networks. Test with small amounts and a wallet you control.

1Create a payment

POST/v1/checkout/links

When a customer wants to pay, your server sends this request. amount_minor is the amount in cents: 1000 means USD 10.00. For a stablecoin payment, the link today asks for the same number of tokens before fees: USD 10.00 asks for 10 USDT or 10 USDC, plus any fee the customer pays. That is the token amount requested, not an exchange rate.

curl https://api.chainmore.io/v1/checkout/links \
  --request POST \
  --header "Authorization: Bearer ${CHAINMORE_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: order-1048" \
  --data '{
    "amount_minor": 1000,
    "currency": "USD",
    "merchant_order_id": "order-1048",
    "return_url": "https://shop.example/thanks"
  }'
  • Idempotency-Key is required on every POST, PUT, PATCH and DELETE. Use one key per order. If a response gets lost, send the same request with the same key: you get the same link back instead of a second one. The repeat does not contain the checkout token, so store the token from the first response before you send the customer to the checkout.
  • merchant_order_id is your own order number. Send it with every link: it keeps an order from being paid twice, even if you create more than one link for it. Use a new number for each order. It is unique per account across test and live mode, so a number you used in test mode cannot be paid in live mode. It comes back in every webhook, so you can match the payment to the order. Allowed: letters, digits and . _ : -, up to 128 characters.
  • return_url is optional and must start with https://. After a successful payment the checkout shows a button back to this address.

The response contains checkout_link_id, checkout_token and available_payment_methods. Save the link ID with your order. The token comes only in the first response. A link stays open for 24 hours.

If that first response is lost, the same request with the same key gives you the same link back with its checkout_link_id, but without a token and with an empty available_payment_methods. A repeat does not recover a lost token, a token cannot be sent again, and a link cannot be cancelled. Check the link with GET /v1/checkout/links/{id}:

  • At or after expires_at, this GET and a retry of the same POST with the original Idempotency-Key report state: expired for an open, unbound link. The retry returns the original link ID without a checkout token.
  • A bound link keeps state: bound and its payment_id after expires_at. Follow that payment and match it against your order before you do anything else.
  • Create a new link, with a new Idempotency-Key and the same merchant_order_id, only if you know the old token never reached the customer, or if the old link's expires_at has passed and it has no payment_id. A link that is still open is not enough: the customer may already have it. If you are not sure, wait until it expires.

2Send the customer to the checkout

Redirect the customer to this address, with the token URL-encoded:

https://checkout.chainmore.io/checkout/?token=<checkout_token>

The checkout does the rest: it shows the payment methods for this link and guides the customer through the wallet steps. Open it as a full page or in a new tab. It does not work inside an iframe on your site. Never put your API key in this URL.

3Receive the result

Add your endpoint in the dashboard under Webhooks. It must be a public https address. You get a signing secret that starts with whsec_; it is shown once. Endpoints and keys are managed in the dashboard only. An API key gets 401 wrong_auth_kind there; only sending a test event also works with an API key. Endpoints belong to a mode as well: a test payment goes to a test endpoint, a live payment to a live endpoint.

When a payment has arrived, we send a POST to your endpoint. The JSON body has event_type, event_id, merchant_order_id and the payment ID.

Ship the order on payment.settled. It comes for every way to pay: USDT and USDC, on the same network or across networks. If you sent no merchant_order_id, the field holds the checkout_link_id.

Want to credit a balance earlier? On payments that arrive on Arbitrum, payments sent to Base from another network, and eligible direct USDC payments on Base, payment.funds_confirmed can come before finality. Your endpoint gets it only if its events list names it. Event names are not checked when you save the endpoint: a misspelled name receives nothing. An empty list means payment.settled only and a list replaces that, so use payment.settled, payment.funds_confirmed. A payment may have no such event, and it promises no time. payment.funds_confirmation_revoked takes the credit back and needs no entry of its own. Hold shipping and withdrawals until payment.settled. That risk stays with you.

Timing for direct USDC on Base

The transfer appears in a Base block. ChainMore sends payment.settled after the network finalizes the transfer. Both measurements below start at the Base transfer block and were observed on 24 November 2026.

ModeEnd of measurementElapsed time
TestPayment marked Confirmed in the merchant receipt16 min 8 sec
LiveMerchant received payment.settled16 min 29 sec

Check every message before you trust it:

  • X-ChainMore-Timestamp is the send time in RFC 3339 UTC, for example 2026-10-07T08:00:00Z. Reject it if it is more than 5 minutes away from your clock.
  • X-ChainMore-Signature is a lowercase hex HMAC-SHA256. The key is your whole whsec_… secret as text. The signed message is the timestamp, a dot, and the raw request body. Compare in constant time.
  • When you rotate the secret in the dashboard, the old one stays valid for 14 days. New messages then also carry X-ChainMore-Signature-Previous, signed with the old secret. Messages queued before the rotation, and their retries, carry only X-ChainMore-Signature with the old secret. Keep the old secret on your server for these 14 days and accept a message when either secret matches either header.
// Node.js with Express. Read the body raw, not as parsed JSON.
import crypto from "node:crypto";

// The whole whsec_… values: the current secret and, for 14 days after a rotation, the old one.
const secrets = [process.env.CHAINMORE_WEBHOOK_SECRET, process.env.CHAINMORE_WEBHOOK_SECRET_PREVIOUS].filter(Boolean);

function signedWith(secret, timestamp, body, signature) {
  const want = Buffer.from(crypto.createHmac("sha256", secret).update(timestamp + ".").update(body).digest("hex"));
  const got = Buffer.from(signature);
  return got.length === want.length && crypto.timingSafeEqual(got, want);
}

app.post("/chainmore/webhook", express.raw({ type: "application/json" }), (req, res) => {
  const timestamp = req.get("X-ChainMore-Timestamp") ?? "";
  const signatures = [req.get("X-ChainMore-Signature"), req.get("X-ChainMore-Signature-Previous")].filter(Boolean);
  const valid = secrets.some((secret) => signatures.some((signature) => signedWith(secret, timestamp, req.body, signature)));
  const fresh = Math.abs(Date.now() - Date.parse(timestamp)) < 5 * 60 * 1000;
  if (!valid || !fresh) return res.sendStatus(400);

  const event = JSON.parse(req.body);
  if (event.test_event) return res.sendStatus(200); // "Send test event": nothing is paid
  if (event.event_type === "payment.settled") {
    markOrderPaid(event.merchant_order_id, event.event_id); // safe to run twice
  }
  res.sendStatus(200);
});
  • Answer with a 2xx status within 10 seconds. Any other answer, 4xx included, counts as failed. Redirects are not followed: a 3xx counts as failed too. We try again after 1 second, 5 seconds, 30 seconds, 5 minutes and 30 minutes. After that the delivery stays failed and you can send it again in the dashboard under Deliveries.
  • The same event can reach you more than once. Process each event_id once, and make "mark order paid" safe to run twice: a resend from the dashboard gets a new event_id.
  • Events can arrive in any order, for example payment.settled before payment.funds_confirmed. Keep one state per payment_id and credit it once.
  • Each event goes to one endpoint of its mode. An endpoint that lists the event comes before one with an empty list; among equals, the oldest one gets it.
  • "Send test event" in the dashboard sends a signed payment.settled with "test_event": true and made-up IDs. Answer 2xx and do not mark anything paid or ship anything for it.
  • Ship the order only after this message. A customer coming back to your site, or a transaction hash, does not prove the payment.

4Check the status yourself

GET/v1/checkout/links/{id}

You can also ask for the state of a link. bound means the customer chose a payment method. It does not mean the order is paid. Follow the payment_id in the response:

  • GET /v1/payments/{id}: paid when the public_status field under payment is completed.
  • GET /v1/payments/{id}/receipt: after payment.settled, the receipt to reconcile with: the on-chain steps with their transactions, and what was debited, charged as fee and received where that is confirmed. requested_amount_minor and requested_currency there are what the payment asked for: for USDT and USDC the token amount in units of six decimals, for example 500000 USDT for 0.50 USDT. They are never a received amount. The summary core_receipt covers USDC payments only; where you bore part of the fee, its merchant_fee_atomic names that part. Other USDT payments have no such summary: the receipt lists the confirmed steps, each in the unit it names, for example 18 decimals on BNB Chain in native_amount_unit. A USDT payment sent from Ethereum to Arbitrum has usdt0_final_delivery instead, in USDT with six decimals: what arrived, the whole fee and, under a fee agreement, your part of it in merchant_fee_atomic. Without a stored agreement that field is absent, which means unknown, not zero.

5Go live

  1. Ask the account owner or an admin to submit the business profile under Onboarding. Check missing information and review status there.
  2. ChainMore reviews your account and approves live access separately if the review is successful. A test payment, submitted profile or API key does not grant live access.
  3. Only after ChainMore has enabled live access and the dashboard offers live mode, deliberately switch to live mode. Test settings do not carry over. In live mode, add your receiving targets and your webhook endpoint again; the live endpoint gets its own whsec_ secret. Then create a live key under API keys (it starts with cm_live_) and replace the test key and the webhook secret on your server.

Live accounts have amount limits agreed with ChainMore. They are checked when the customer pays, not when you create the link: a link above them is created, but the checkout cannot take the payment.

For help, email support@chainmore.io.

Errors and retries

Every error comes as application/problem+json with a stable code, a docs_url that explains it, and a correlation_id. Match on code, not on the text. Send us the correlation_id when you need help.

You seeMeaningFix
400 idempotency_requiredThe header is missing.Send Idempotency-Key, one value per order.
401 unauthorizedThe key is missing or wrong.Check Authorization: Bearer cm_test_….
401 wrong_auth_kindThis route is for the dashboard only.Manage keys and webhooks in the dashboard.
No payment method in the checkoutNo receiving target in this mode yet, or an EUR link in live mode.Add one under Receiving targets. Use USD for live payments.
Checkout page shows 404Wrong host.The checkout lives on checkout.chainmore.io, not on the API host.
Signature never matchesThe body was parsed before the check.Read the raw body and use the whole whsec_… value as key.
429 rate_limitedToo many requests.Wait a moment, then retry with the same Idempotency-Key.
